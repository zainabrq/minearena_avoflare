# Sensor quality and artifact handling

**MineArena PS03 | Frozen Architecture V4.1 | Specification v1.0**

Engineering prototype only; clinical decision support, not diagnosis. Implementation, integration and clinical validation pending. All numeric timing and decision heuristics below are configurable engineering defaults, not clinical guidelines. Do not add architecture components or use SNN.

## 1. Inputs and separation
Operate in existing secure gateway/quality and expert/trust components, not a new agent. Preserve original FHIR observation and raw source values. Assess each sample and window using timestamps, units, source quality metadata, recent history. Labels from simulator ground truth are offline only; device-reported quality is allowed if genuinely available, authenticated and distinguished from inferred quality. Quality categories valid/suspect/invalid/missing/stale. A physiologically extreme value is not automatically invalid. Independent safety receives raw concerning values and quality status; artifact handling cannot silently clear existing alerts.

## 2. Deterministic checks (engineering defaults)
- Missing/null/NaN: normalize to null, explicit reason, never zero; FHIR dataAbsentReason. Nonfinite, negative HR/RR, SpO2 outside 0–100, impossible unit or malformed payload: invalid for scoring, preserve raw in audit, technical verification. Temperature engineering sensor range 20–50 C: outside suspect/invalid-for-score, urgent verification if plausible clinical concern; not a medical normal range. HR/RR/SpO2 zero: suspect unless confirmed device fault or verified clinical observation; urgent verification per 07. Do not erase zero in BIDMC.
- Flatline: >=10 source seconds of identical quantized values (HR/RR tolerance 0.1 unit; SpO2 0.1 pp; Temp 0.01 C) with >=80% coverage and no gap >2 nominal intervals. Flag suspect, not proof of fault; stable SpO2 and temperature often repeat, so never invalidate solely by flatline. HR flatline coupled with SpO2 dropout is stronger evidence.
- Motion/outlier candidate: adjacent valid sample change HR>=30 bpm, RR>=10/min, SpO2>=5 pp, Temp>=0.5 C within <=2 source seconds, or authenticated motion flag. Flag abrupt change for verification, not confirmed artifact; true spikes must still be detected. Reversal within 10s, contemporaneous device motion/quality metadata or repeated implausible spikes strengthens suspicion. No suppression based solely on absent cross-vital changes.
- Joint probe removal: SpO2 null or raw zero and HR flatline overlapping >=10s with reliable time coverage; mark likely probe fault, technical alert, no score for corrupted SpO2/HR during affected interval. Before pattern established, flag possible fault and urgent verification as applicable. Confirmed fault requires trustworthy device indication or human verification; pattern alone is not confirmation. Underlying deterioration may coexist. Assess RR/Temp and any remaining reliable data; retain unresolved clinical concern. Restore eligibility only after 10s reliable fresh data and quality recovery; separate clinical recovery policy in 07.
- Gap/dropout: missing expected samples per vital; source-time gaps >2 nominal intervals interrupt persistence. Mark stale after 15s; monitoring interruption after 30s without any authenticated fresh sample (wall-clock watchdog in live mode, replay source time for scenario evaluation; paused replay explicitly marked). Technical alert separate from clinical alert. Partial missing -> degraded. Duplicates idempotent; out-of-order retained for audit but cannot overwrite newer state. Use sequence and identity checks.

## 3. Alert handling
Confirmed invalid/artifact-only measurements do not independently generate definitive clinical alerts. Issue technical verification alert, keep uncertainty, evaluate reliable signals and prior unresolved alerts. Suspect critical measurement requires immediate safety verification; no wait for 30s persistence. If genuine abnormality supported by reliable evidence, escalate despite simultaneous artifact. Never substitute interpolated/model-estimated values into clinical scores. Store suspect/invalid data with provenance; do not convert observed zero to normal. For false-alert evaluation compare clinical alert episodes against offline labels, report technical alerts separately.

## 4. Output and tests
Quality output per vital: raw value/ref, normalized value|null, quality, reason codes, flags, source and assessment timestamps, freshness, coverage, fault pattern confidence (categorical not calibrated probability), evidence refs, policy version. Window quality retains min/max, invalid counts, missing counts and gaps. Monitoring state normal/degraded/interrupted; technical alert ID and lifecycle. Test isolated motion, genuine spike, flatline alone, simultaneous SpO2 missing+HR flatline, RR zero, genuine RR deterioration during probe removal, gaps across windows, duplicates and stale data. See 08. MATLAB owns generating faults; backend owns inference. P010 joint fault implementation is pending, not assumed completed.
