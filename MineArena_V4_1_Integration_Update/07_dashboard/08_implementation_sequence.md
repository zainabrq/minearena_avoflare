# 08 | Claude build sequence and demonstration

## Implementation gates
1. Inspect repository, actual asset files, backend OpenAPI/contracts and simulator interfaces. Read all specs and current policy. Produce mapping of implemented/missing APIs, asset audit, scope plan. Do not change V4.1 or clinical algorithms.
2. Create React/TypeScript shell, tokens, accessible components, role-aware navigation, login using supplied logo/video. Add loading/error/empty states and persistent disclaimer. Establish integration test harness. Use clearly labeled fixtures only during UI development, never live mode.
3. P0 monitoring: authorized patient queue, session selector, patient detail, four actual trends, partial NEWS2, context facts, baseline and quality. Connect live snapshot/events, verify identity isolation and stale state. Immediate safety independent of normal window and model.
4. Alert center: actual episodes, three explanation fields, categories, acknowledge/resolve authorized server actions, recurrence and unresolved Urgent. Verify artifact-only and simultaneous genuine deterioration. Add FHIR inspection, actual persistence status.
5. Evaluation: real MATLAB and BIDMC controls, stable/slow/artifact scenarios, source time vs wall clock, actual comparator result and report. Test five qualifying synthetic profiles influence monitoring. Mandatory requirements first.
6. P1 spatial: two existing watch videos and fallbacks, confirmed presentation state, no extra media. Lazy procedural twin and textual manifest, actual forecasts/uncertainty, expert and trust outputs, isolated counterfactuals. No fake estimates if model pending.
7. Care and patient: approved plans and medication review, progress/history/reports, patient auth, symptom check-ins if supported. Never generate clinical orders. Optional escalation/translation only if actual backend supports.
8. Run acceptance matrix, visual audit, responsive/accessibility tests and production build. Fix actual blockers. Record measured demo results, warnings and missing dependencies; no fabricated passes.

## Demo run (recommended order)
- Login into clinician workspace, show Avoflare branding and disclaimer.
- Overview shows actual cohort. Choose P001 and show real patient history, four vitals, scoring, baseline and evidence.
- In evaluation start slow deterioration; monitor live updates, baseline deviation, actual alert. Explain triggering reading, rule, relevant fact. Show fixed-threshold vs V4.1 measured detection lead time/alerts per patient-day if run complete.
- Replay stable and artifact-only probe removal. Show attached clip then removed clip only on confirmed simulated event; technical alert vs clinical decision, missing data and quality. If no confirmed presentation state, show suspected removal without asserting device state. Demonstrate simultaneous genuine deterioration if available.
- Compare authorized P002-H overlay to P002 (explicitly hypothetical) and personalization; never imply original P002 authorized Scale2.
- BIDMC replay, record identity and actual three available vitals, no temperature. Show stored HAPI Observation and validation evidence.
- Show twin textual manifest, four physiological experts, forecast/uncertainty only if implemented, otherwise explicit unavailable. Counterfactual only actual result.
- Show patient approved recovery flow if implemented, then actual report. State engineering prototype limitations.

## Mandatory requirement traceability
3.1 FHIR ingestion/store: FHIR records and validation actual retrieval. 3.2 MATLAB/BIDMC: evaluation controls plus real monitored sessions. 3.3 >=5 Synthea profiles with conditions/medications affecting scoring: profile/context and comparative evidence, not count alone. 3.4 personalized NEWS2: component scores, scale and rolling baseline. 3.5 artifact: quality/device and separate technical alerts. 3.6 clinician dashboard: live monitoring, patient context, scoring, Watch/Review/Urgent and reading/rule/fact explanation. 3.7 evaluation: actual replay and comparative report. All code written during hackathon, working functionality required, no slide-only demonstration.

## Definition of done
Runnable frontend with documented setup, actual integration mapping, no hardcoded live values, correct access boundaries, no misleading media state, mandatory flows exercised, design restrictions satisfied, no errors in primary flows, measured test results and explicit blockers. Optional visual features never block core monitoring. Deliver source, build/test commands, screenshots, actual evaluation outputs, and known issues. Do not claim clinical validation.
